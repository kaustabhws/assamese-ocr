# Deployment

## Portable model bundle

The recognizer export uses standard ONNX operators with dynamic input width and fixed height 48. The tested Python runtime uses ONNX Runtime CPU. The same recognizer graph is suitable for ONNX Runtime on Windows, Linux, macOS, Android, and iOS, subject to testing on the actual target.

The whole pipeline has three weight files:

- Assamese recognizer: generated by `scripts/export_recognizer.py`
- text detector: the RapidOCR package's mobile DBNet model
- semantic layout: `artifacts/layout/docling-layout-heron-int8.onnx`

The current balanced layout file is about 69 MB, so very small mobile applications may choose to omit semantic classes or later replace it with a distilled student. Do not describe the current bundle as working on “every device”; name the tested operating system, CPU, memory, runtime, and latency.

## Runtime contract

Recognizer input is float32 `[batch, 1, 48, width]`, where white is `0`, black is `1`, and width is divisible by four. Output is float32 `[batch, time, classes]`; CTC blank is index zero. The adjacent JSON file contains the exact vocabulary and its SHA-256.

Layout input is uint8 RGB `[1, 3, 640, 640]` plus original target size `[width, height]`. It returns labels, pixel-space `xyxy` boxes, and scores.

## Deployment checks

For each target platform:

1. verify at least 100 golden crop outputs against the PyTorch checkpoint;
2. compare FP32 and INT8 CER, especially `ৰ` and `ৱ`;
3. measure cold start, median, p95, peak memory, and package size;
4. run complete scanned pages, not only isolated words;
5. retain the canonical JSON so export/UI changes do not alter recognition evidence.
